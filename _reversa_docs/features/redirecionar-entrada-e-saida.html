Visão Geral

Abre os arquivos de <, > e >> e liga os descritores ao stdin e ao stdout de cada comando, com prioridade sobre os pipes. Os arquivos são abertos no shell antes de qualquer execução, e os dup2 são feitos dentro de cada filho. O heredoc (<<) entra pelo mesmo mecanismo de entrada, e a leitura do conteúdo fica em ler-heredoc 🟢.

Responsabilidades

  • Abrir, no shell e antes dos forks, todos os arquivos de redirecionamento da linha 🟢
  • Escolher, para cada comando, a entrada e a saída efetivas 🟢
  • Fazer dup2 dos descritores escolhidos no filho e fechar o resto 🟢
  • Informar erros de abertura 🟢

Regras de Negócio

Abertura (no shell, antes da execução)

  • RD-01: < alvo → open(alvo, O_RDONLY) 🟢
  • RD-02: > alvo → open(alvo, O_RDWR | O_CREAT | O_TRUNC, 0644) 🟢
  • RD-03: >> alvo → open(alvo, O_RDWR | O_CREAT | O_APPEND, 0644): echo a > f1, echo b >> f1 → a, b 🟢 (observado)
  • RR-01: todos os arquivos de saída da linha são criados ou truncados antes da execução, inclusive os que não serão usados: echo c > f2 > f3 → f2 vazio, f3 com c 🟢 (observado), igual ao bash
  • O alvo é sempre um WORD literal (sem $), por causa da gramática (BUG-13) 🟢
  • RR-06 / BUG-01: erro ao abrir arquivo de saída → perror(alvo) e o shell cai: echo x > o3 > /nonexistent/x → /nonexistent/x: No such file or directory seguido de segfault (código 139) 🟢 (observado)

Escolha da entrada (por comando)

  • RD-04: se o nó imediatamente anterior ao comando é PIPE, REDI ou HERE, o stdin vem dele 🟢
  • RD-05: depois, os nós seguintes até o próximo PIPE são percorridos; o último REDI/HERE vence: cat < in1 → conteúdo de in1 🟢 (observado)
  • RN-43: redirecionamento de entrada vence o pipe: echo z | cat < in1 → conteudo 🟢 (observado), igual ao bash
  • RR-03: < in1 cat funciona porque o < está imediatamente antes do comando 🟢 (observado)
  • BUG-09 / RR-05: < inexistente cmd não dá erro; o comando roda com o stdin original e $?=0 🟢 (observado). ⚠️ O bash informa o erro e não executa
  • cmd < inexistente → inexistente: No such file or directory em stderr, o comando não executa, $?=1 🟢 (observado)
  • RR-04: ls | > o1 wc -l: o nó anterior a wc é REDO, que não é PIPE nem entrada, então wc não lê o pipe e fica com o stdin original (o terminal, numa sessão interativa: espera digitação até Ctrl-D); a saída vai para o terminal e o1 fica vazio, mas é criado 🟢 (código: src/fd_handler.c:9-12; observado com stdin já em EOF: wc imprime 0). [Revisão: corrigida a afirmação anterior de que wc lia o1.] ⚠️ No bash, wc lê o pipe e escreve em o1

Escolha da saída (por comando)

  • RD-06: os nós seguintes até o próximo PIPE são percorridos; o último REDO/REDA vence 🟢
  • RN-43: redirecionamento de saída vence o pipe: echo a > f5 | cat → cat não recebe nada 🟢 (observado), igual ao bash
  • BUG-08 / RR-02: redirecionamento de saída antes do comando é ignorado: > f4 echo d → d no terminal, f4 vazio (mas criado) 🟢 (observado). ⚠️ No bash, d vai para f4
  • cat < in1 > o2 → o2 com o conteúdo de in1 🟢 (observado)

Outros

  • Não há suporte a 2>, &>, <>, >| nem a descritores numerados 🟢
  • ✅ L-07 (decidida em 2026-11-22, [Revisão]): documentar o comportamento atual. As ⚠️ DIVERGÊNCIAS desta unit são o comportamento especificado, não defeitos a corrigir. (Pendência original: BUG-01 (crash), BUG-08, BUG-09 e RR-04)

Nó de redirecionamento: args = {"REDO"|"REDA"|"REDI"|"HERE", alvo} e fd[0] = descritor aberto (no HERE, fd = pipe do conteúdo) 🟢.

Fluxo Principal

  1. Abertura (open_fds, pai, src/fd_handler_utils.c:15-44): `` para cada nó: REDI → fd[0] = open(alvo, O_RDONLY) # -1 se não existir, sem mensagem aqui REDO → fd[0] = open(alvo, O_RDWR|O_CREAT|O_TRUNC, 0644) REDA → fd[0] = open(alvo, O_RDWR|O_CREAT|O_APPEND, 0644) se -1: perror(alvo); free_line(line) # o laço continua sobre nós liberados (BUG-01) PIPE → pipe(fd)
  2. No pai, por nó (init_fork, src/exec/init_fork.c:22-24): ao passar por um nó REDO/REDA, fecha fd[0] 🟢. Os REDI não são fechados no pai 🟢 (observado na revisão de 2026-11-22)
  3. No filho do comando (make_redirections, src/exec/exec_path.c:41-49):
    1. find_input (src/fd_handler.c:15-42): `` se prev é PIPE, REDI ou HERE: dup2(prev->fd[0], 0) input = 0 para cada nó seguinte até PIPE: se REDI/HERE: input = nó->fd[0] se !file_exists(nó->fd[0]): "<nó->args[1]>: No such file or directory"; retorna -1 se input > 0: dup2(input, 0) retorna input
    2. find_output (src/fd_handler.c:44-70): `` output = 1 para cada nó seguinte: se PIPE: se output == 1: output = pipe->fd[1]; pare se REDO/REDA: output = nó->fd[0] se output != 1: dup2(output, 1); close(output)
    3. close_fds: fecha todos os fds de operadores da lista
    4. exec_path: se input < 0 → free_exit(1)
  4. Fim da linha: main_loop restaura stdin/stdout com dup2(std_fd) (unit iniciar-sessao-e-ler-comando) 🟢

Por que > f4 echo d ignora o arquivo

A lista é [REDO f4] [echo d]. find_output só olha para frente a partir do comando, e o REDO está atrás. find_input olha para trás, mas só procura entrada 🟢.

Por que ls | > o1 wc -l não lê o pipe

A lista é [ls] [PIPE] [REDO o1] [wc -l]. Para wc, o prev é REDO, que não satisfaz prev é PIPE || is_redirect_input(prev); nenhum dup2 de entrada é feito e o laço para frente não encontra REDI/HERE. O stdin continua o original (o terminal) 🟢. find_output olha só para frente e não acha REDO, então a saída também é a original 🟢. O REDO o1 fica atrás de wc e só tem o efeito de criar/truncar o1 em open_fds 🟢. [Revisão 2026-11-22: corrigida a versão anterior, que dizia que wc lia o1.]

Verificação file_exists em nós de comando (RR-07)

Dentro do laço de find_input, file_exists(temp->fd[0]) também é chamado em nós de comando seguintes (cat < f -e → nó -e). Nesses nós, fd[0] é o pedaço baixo do ponteiro bin (union), e o resultado depende do valor do ponteiro 🟡.

Fluxos Alternativos

  • Entrada inexistente depois do comando: find_input acha fd[0] = -1 → mensagem → free_exit(1) 🟢 (observado)
  • Entrada inexistente antes do comando: prev é REDI com fd[0] = -1; dup2(-1, 0) falha em silêncio e o laço para frente não encontra nada; o comando roda 🟢 (observado)
  • Saída impossível: free_line dentro de open_fds libera a lista que o laço ainda percorre; o retorno a exec_pipe_line usa a linha liberada → segfault ou abort 🟢 (observado: código 139)

Dependências

  • executar-comando-simples: lista de nós; exec_path chama make_redirections
  • executar-pipeline: compartilha find_input/find_output (ramo PIPE)
  • ler-heredoc: fornece o fd dos nós HERE
  • POSIX: open, dup2, close, fstat

Estado Interno

Os fds vivem no union de cada nó durante a linha. O pai fecha os de saída em init_fork; os de pipe e heredoc em init_fork/close_here_doc. Os de entrada (REDI) ficam abertos e vazam para os filhos seguintes 🟢 (observado na revisão de 2026-11-22).

Observabilidade

perror(alvo) (saída), <alvo>: No such file or directory (entrada, escrito pelo filho) 🟢.
